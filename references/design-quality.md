# 设计与评分要求

本规则来自用户提供的要求；设计质量及新增测试设计质量按2026-11-05修订内容执行，其余文档质量要求保留。两项各自使用0%、30%、60%、80%、100%五档及最多向下两档的综合质量扣档规则；没有提供维度权重或总分算法，不得自行发明或合并总分。仅评价与需求相关的有效设计，不照抄评分话术充当设计内容。

## 总体要求

使用公司IPD规定模板，需求分析从客户角度出发。设计易扩展、易落地、模块耦合少，可靠性、安全性、可信要求全面。设计文档有效指导编码，技术评估结论能支撑决策。社区设计文档遵循其社区规则；不能自行把本模板认证为公司最新IPD版本。

## 1 设计质量（修订）

目标：设计文档能够有效指导编码，评估报告能支撑技术决策。参考评分方案选择最符合要求的Top2设计文档；这是评审选样规则，不要求每次生成两篇。

负向案例：一句话需求或设计，不能指导开发工作；评估报告结论不清晰，不能支撑技术决策；安全设计未考虑充分导致ICSL送检严重问题或版本延期等。

| 条目 | 修订要求 | 在文档中落实 |
|---|---|---|
| A.a 需求满足 | 需求背景清晰 | 明确谁（用户/角色）在什么场景遇到什么痛点；解释业务价值或技术价值（Why），不能仅罗列功能；界定哪些场景做、哪些不做 |
| A.b 需求满足 | 设计方案完全满足需求 | 需求、实现和验收逐项对应，说明覆盖关系与缺口 |
| B.a 方案可行 | 详细设计方案清晰，包含现有代码架构与设计方案的关系 | 说明现有职责、依赖、调用链与本次方案如何衔接；定位复用、新增、修改、替换的模块及影响，有代码证据才引用实际路径和类名 |
| B.b 方案可行 | 合理的代码、类、接口设计 | 职责与依赖方向、方法签名、参数和返回结构、边界与异常处理明确，足以指导实现 |
| B.c 方案可行 | 与周边组件的交互关系设计 | 交互对象、接口、依赖方向、协议及失败处理；文档本身不涉及则说明原因 |
| B.d 方案可行 | 合理的性能设计 | 负载、容量、资源预算、瓶颈、目标及验证方式；文档本身不涉及则说明原因 |
| C 易用性 | 考虑用户使用的易用性，接口符合用户使用逻辑 | 角色操作路径、默认值、输入限制、状态反馈、错误提示及恢复方式按场景落实 |
| D 可观测性 | 关键业务日志、Metrics、Tracing | 定义日志格式、级别、脱敏规则；定义监控指标及口径；说明链路追踪接入和关联上下文传播方案 |
| D 可维护性 | 清晰部署方案，支持滚动升级和回滚；健康检查；运维手册 | 说明部署顺序、混合版本约束、滚动升级和回滚条件；定义健康检查接口与判据；提供真实运维手册链接或具体操作说明 |
| D 安全性（ICSL合规） | 认证、授权、传输/存储加密、SQL/XSS防注入、审计日志；说明如何满足ICSL送检 | 明确威胁与措施、适用边界、送检要求对应关系、验证方法和证据状态，不能只写“符合ICSL” |
| E 方案扩展性 | 详细描述后续可能扩展的方向、应对方案、设计模式；保证前后一年的兼容；包含下列四项之一 | 给出扩展点、触发条件、模式选择理由及兼容对象、时间基准、升级回滚与验证安排，并至少有效覆盖下述一个方向 |

E的四个可选内容，至少包含一项，不得擅自改成四项都必填：

- **约束与假设**：明确当前设计约束、假设，以及假设变化时的应对方案。
- **设计模式**：采用插件化、配置化、策略模式、观察者模式等支持后续扩展，解释具体扩展点和适用理由，不能仅列模式名。
- **兼容性承诺**：明确接口版本管理策略，以及向前兼容（旧客户端调用新服务）、向后兼容（新客户端调用旧服务）的具体措施。方向用语按本次评分原文，不自行对调。
- **未来规划**：包含“后续演进方向”或“已知待办”章节，描述未来1年的扩展路线；选此项时可在原扩展性章节内增加相应子标题，不改变模板原表格。

### 设计质量评分档位

| 档位 | 比例 | 原文条件 |
|---|---|---|
| 第一档 | 0% | 不满足A |
| 第二档 | 30% | 仅满足A |
| 第三档 | 60% | 满足A和B |
| 第四档 | 80% | 在第二档前提下，满足C、D、E中的两项 |
| 第五档 | 100% | 满足所有A、B、C、D、E |

第四档的“第二档前提”按用户原文保留，不擅自改为“第三档”或追加B为80%的必要条件。自检应列出A至E实际满足情况及证据，不能只给一个档位而隐藏未满足项。

上述部分均需达到有效设计才算满足；过于简陋、无效设计算不满足。需求不涉及对应设计时，文档说明具体不涉及原因，视为完成对应设计。综合所有举证文档质量，质量偏差较大时适当扣分，向下不超过2档；没有提供逐项固定扣分值，不自行编造。

### 编写落实与证据边界

评估内容应给出明确推荐结论、备选方案、比较依据、关键取舍、适用条件及未决风险，能据此进行技术决策；仅在存在实际评估对象时编写，不为评分虚构独立评估报告。

未取得现有代码时，明确架构关系分析的资料缺口、暂定接入点及验证方式，不能将拟新增类写成已存在类。ICSL实际基线、版本、检查项和测试报告只使用有来源的资料；未提供时列出待确认要求、当前设计措施、验证/送检计划及证据缺口，不能声称已通过ICSL或已有送检结论。所需运维链接缺失时提供具体说明，不编造链接。部署、健康检查、Tracing或加密确实不适用时逐项说明原因和边界，不以统一“不涉及”代替分析。

## 2.1 文档要素完整

四项全部满足是此维度原始满分条件：

- a 使用公司IPD规定模板。
- b 所有相关章节均有内容说明，不能只有章节标题。
- c 考虑异常场景、接口设计及周边组件交互。
- d 明确接口设计和后续扩展策略。

负向案例：非标准IPD文档；相关章节缺失或只有标题。确实不适用的章节保留并给出具体原因。模板标记“可选”不等于可以跳过与需求相关的DFX内容。

## 2.2 文档易于理解

五项全部满足且图文表达正确是此维度原始满分条件：

- a 有清楚的业务流程说明，避免冗长的实现细节/伪代码打断业务理解。原文此句存在转录不顺，按此含义规范化，不解读为禁止全部伪代码。
- b 合理应用UML类图、流程图等，用图表和简明文字解释设计思路。
- c 数据结构定义清晰，涉及多系统交换时用数据流图说明模块间流动。
- d 合理应用架构关系图、时序图说明整体功能、关系和约束。
- e 接口定义与变化清晰，可用表格表达。

负向案例：没有上下文、没有必要图文辅助、仅业务流水记录而无业务抽象。每章一个图表不是达标依据。应解释图中边界、关系、关键决策与实现约束。

## 3 测试设计质量（新增）

目标：测试用例作为门禁，应有效看护代码质量。具体全面：覆盖各类场景，明确预期行为。参考评分方案选择最符合要求的Top2设计文档，同样不要求每次生成两篇。

负向案例：同义反复、恒定通过；与真实业务场景相悖；不可观测、标准模糊；不可复现、结果不定。

| 条目 | 原始评分要求 | 有效测试设计的落实方式 |
|---|---|---|
| a | 仅涉及正常场景 | 定义真实业务的正常路径、可执行步骤与可观察预期结果；此项是正常场景覆盖基础，不限制更高档仅写正常场景 |
| b | 考虑异常场景和边界场景 | 覆盖适用的非法输入、权限失败、依赖失败、超时、资源不足，以及长度、值域、数量、空值和状态边界；注明检测和恢复预期 |
| c | 考虑多参数组合测试或不变量测试 | 至少设计适用的一种：明确参数取值、有效/无效组合、约束和预期；或明确跨输入/状态始终应成立的业务不变量及验证动作 |
| d | 考虑性能、兼容性和周边组件协作 | 分别说明负载与性能阈值、版本组合与兼容预期、真实组件/契约协作与故障反馈；涉及的子项有效覆盖，不以其中一项代替全部 |

### 测试设计质量评分档位

| 档位 | 比例 | 原文条件 |
|---|---|---|
| 第一档 | 0% | 不满足a |
| 第二档 | 30% | 仅满足a |
| 第三档 | 60% | 满足a和b |
| 第四档 | 80% | 在第二档前提下，满足c或d中的一个 |
| 第五档 | 100% | 所有均满足 |

第四档同样保留“第二档前提”，不改为“第三档”或擅自增加b为80%的必要条件。c为“多参数组合或不变量”，无需无依据地强制两者都做；d包含性能、兼容性和周边组件协作三方面，应分别判断适用性和覆盖证据。

上述部分均需达到有效设计才算满足；过于简陋、无效设计算不满足。综合所有举证文档质量，质量偏差较大时适当扣分，向下不超过2档。此新增维度未单独重述“不涉及即可完成”的规则：不适用项仍需具体说明原因及边界；在没有明确评审口径时记录为“不适用/判分待确认”，不得为了满档将不存在的系统、指标或协作关系写成已覆盖。

### 测试门禁的写作检查点

以下是使评分要求能够指导测试实现的检查点，不是另加评分项：

- **业务有效**：每条用例关联R/F/I编号和要看护的行为；断言能区分正确与错误实现。不能以“调用成功则成功”、断言常量、复制被测实现或永远为真的比较充当验证。
- **可观测**：明确响应码/错误码、返回字段与数量、持久化副作用、隔离性、资源释放或日志/指标等观察点；给出精确判据或容差，不能仅写“正常”“符合预期”。
- **可复现**：给出环境/版本、初始数据、前置状态、输入、故障注入方式、步骤和清理；涉及时间、随机性、并发或外部依赖时说明固定时钟、种子、同步点、受控依赖等适用控制，避免无界等待和依赖偶然时序。
- **组合/不变量**：组合测试不能只堆独立单参数用例；说明选择的参数组合、约束及预期。不变量例如租户隔离、金额守恒、分页不重复，应明确适用前提及验证结果，不能把与业务无关的恒真条件写成不变量。
- **性能/兼容/协作**：性能用例定义数据规模、并发、持续时间、采样/统计口径、阈值与失败判据；兼容用例列出旧客户端/新服务和新客户端/旧服务等适用组合与观察点；协作用例验证真实协议、数据流及依赖异常，不能以只测本模块的桩返回值代替协作覆盖。
- **门禁**：说明用例如何进入适用的单元/接口/业务/异常测试层、何时执行、哪些失败阻断提交或发布，以及失败定位与重跑条件；无流水线资料时写为建议接入方案，不声称已启用或已执行通过。

所有测试内容填入模板已有6.1至6.4及原九列表：正常与组合场景放6.3、接口契约与组件协作放6.2、异常/性能/兼容场景按实际组织并在相应位置交叉引用。参数组合、不变量、门禁说明可用段落补充，不新增、拆分或改造原表。

## 实施所需的内容深度

下列为执行上述要求的写作检查点，按适用性覆盖，不是用户另行规定的评分项。

- 需求/验收：R-ID、角色、前置条件、输入、成功结果、边界、验收判据；区分客户约束与建议目标。
- 接口：I-ID、所属模块、协议/方法/路径或函数签名、请求字段类型/必填/约束、响应与示例、错误码、鉴权、超时/重试、幂等与并发、版本及变更影响。
- 数据：字段名、类型、单位、可空、默认值、约束、索引、拥有者；持久化/事务/一致性/迁移/清理策略；敏感数据分类与保护。
- 关键流程：正常、参数错误、权限不足、依赖失败、超时、重复提交、并发冲突、资源耗尽等与本需求有关的分支；状态与错误码在图、接口、文字、测试中一致。
- 类与解耦：单一职责、依赖方向、接口隔离、扩展点、现有代码架构与方案的衔接、复用/新增/修改位置、重构理由；有证据才引用真实代码路径和行号。
- 可靠性：故障域、超时预算、重试上限与退避、幂等、熔断/降级、资源释放、恢复和回滚；不要求无意义地套用所有机制。
- 安全：输入校验、跨信任域交互、竞争条件、文件/临时文件/解压、网络通信、认证授权、传输/存储加密、SQL/XSS防注入、敏感信息与审计；说明ICSL送检要求如何落实，仅引用有来源的公司基线。
- 性能：规模、并发、延迟、吞吐、内存/CPU/存储约束和测试方式；未测试不能写“已满足”。
- 扩展兼容：以目标版本/时间为基准，分别说明过去一年与未来一年接口、配置、数据和部署；未来部分是兼容设计承诺/策略，不是已验证事实。缺少版本边界时列入待确认项。
- 测试：TC-ID、对应R/F/I-ID、前置、输入、动作、可观察结果、验证层次；覆盖单元、接口、业务、异常，性能/安全测试放相应章节。
- 资料修改：用户手册、接口文档、配置参考、运维/升级/回滚说明、通信矩阵等，说明改什么、何时同步；无明确人员时不伪造负责人或审批意见。

## 自检记录

工作目录中分别记录设计质量A至E（含各子项）、测试设计质量a至d及原文档质量2.1/2.2的“条款 | 章节位置/图表/接口/测试ID | 满足/不适用/缺口 | 有效性依据与原因/修复”。逐项标识资料不足和判分待确认，不能用篇幅、表格数、存在标题或结构检查通过代替有效设计。

按两套原文档位分别记录自检符合条件、未满足项和依据；若涉及所有举证文档的综合扣档，记录质量偏差、基础档位、调整依据及调整后档位，下调不得超过2档。未获得所有举证文档时不能声称完成综合评定，不编造固定扣分、权重、总分或正式评审结论。文档质量2.1和2.2未给五档规则，不套用本次两套比例。

检查模板原有五张表格及每个叶子章节；核对R-F-UC-I-TC关系、测试可观测/可复现和门禁判据；检查来源、假设和设计选择是否混淆。Top2只用于评审选样，不要求自动生成两篇文档。评分证据留工作目录，最终DOCX写具体设计，不复制评分表充当正文。
